# Портфолио с собственной CMS

Сайт-портфолио, которым можно пользоваться: публичная часть (проекты, блог,
поиск, «Обо мне») плюс закрытая админка, где контент создаётся, публикуется
и редактируется через веб-интерфейс.

Главная идея — не «сверстать страницу о себе», а сделать инструмент, которым
я сам пользуюсь. Именно админка оправдывает базу данных и даёт те задачи,
которые интересно решать: авторизация, роли, миграции, серверные мутации,
инвалидация кэша.

## Стек

| Слой | Выбор |
| --- | --- |
| Фреймворк | Next.js 16 (App Router, React Server Components) |
| Язык | TypeScript, strict |
| Стили | Tailwind CSS v4 |
| База данных | PostgreSQL (Neon) |
| ORM | Prisma 7 |
| Валидация | Zod 4 |
| Авторизация | Собственные сессии на подписанных cookie (`jose`) |
| Хранилище файлов | Vercel Blob |
| Тесты | Vitest (модульные), Node-скрипт (интеграционные) |

## Что умеет

**Публичная часть**

- Главная с избранными проектами и свежими статьями
- Список и детальные страницы проектов
- Блог с пагинацией и фильтром по тегам
- Поиск по названиям и тексту проектов и статей
- «Обо мне» — текст хранится в базе, а не в коде
- `sitemap.xml`, `robots.txt`, RSS-лента
- Динамические OG-картинки для статей и главной
- Структурированные данные JSON-LD
- Тёмная тема без «вспышки» при загрузке

**Админка**

- Вход по email и паролю, пароль хранится хешем (`bcrypt`)
- Сессия в httpOnly-cookie, защита всех разделов
- CRUD проектов и статей
- Черновики и публикация
- Теги создаются автоматически при первом упоминании
- Время чтения считается по тексту
- Slug генерируется из заголовка с транслитерацией кириллицы
- Загрузка обложек с превью
- Дашборд со счётчиками

## Быстрый старт

Нужны Node.js 20.19+ и база PostgreSQL. Проще всего взять бесплатную
в [Neon](https://neon.tech) — она же подойдёт для продакшена.

```bash
# 1. Зависимости
npm install

# 2. Переменные окружения
cp .env.example .env
# заполните DATABASE_URL и AUTH_SECRET (см. ниже)

# 3. Схема базы и демо-данные
npm run db:migrate
npm run db:seed

# 4. Запуск
npm run dev
```

Сайт откроется на http://localhost:3000, админка — на `/admin`.

**Демо-доступ:** `admin@example.com` / `admin12345`. Этот пароль задан в сиде
и предназначен только для локального запуска — в реальном развёртывании
его нужно сменить.

### Переменные окружения

| Переменная | Назначение |
| --- | --- |
| `DATABASE_URL` | Строка подключения к PostgreSQL |
| `AUTH_SECRET` | Секрет для подписи сессионных cookie |
| `NEXT_PUBLIC_SITE_URL` | Публичный адрес сайта (метаданные, sitemap, RSS) |
| `BLOB_READ_WRITE_TOKEN` | Токен Vercel Blob для загрузки обложек |

`AUTH_SECRET` генерируется так:

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

Файл `.env` в репозиторий не попадает — он в `.gitignore`.

Без `BLOB_READ_WRITE_TOKEN` загрузка файлов отключена, но обложку можно
указать ссылкой вручную.

## Решения, которые стоит объяснить

Этот раздел — самая полезная часть README: здесь про то, почему сделано
именно так и какие у выбора компромиссы.

### Почему свои сессии, а не Auth.js

Для одного администратора Auth.js — лишний слой абстракции поверх задачи,
которая решается полусотней строк. Своя реализация даёт полный контроль
и понимание механики: почему токен нельзя держать в `localStorage`, что
делают флаги `httpOnly` и `SameSite`, как подписывается payload.

Токен — это JWT, подписанный `HS256`. Важно понимать: подпись гарантирует
**неизменность**, но не **секретность** — содержимое cookie читается кем
угодно. Поэтому в токене только идентификатор, имя и роль. Пароль и его хеш
туда не попадают никогда.

Auth.js стоит брать, когда нужны внешние провайдеры (Google, GitHub),
несколько ролей со сложной логикой доступа или готовые экраны входа.
Для одного владельца сайта это избыточно.

### Почему защита стоит в двух местах

Layout админки проверяет сессию и закрывает интерфейс. Но Server Action —
это отдельная точка входа: её можно вызвать HTTP-запросом напрямую, минуя
страницы. Поэтому каждая операция начинается с `assertUser()`.

Проверка в layout защищает глаза. Проверка в действии защищает данные.

### Почему Prisma 7 требует драйвер-адаптер

В седьмой версии Prisma отказалась от Rust-движка запросов в пользу
компилятора на TypeScript, а соединение передала драйвер-адаптерам. Отсюда
следствия, которые видно в коде:

- клиент создаётся поверх `@prisma/adapter-pg`, а не сам по себе;
- строка подключения живёт в `prisma.config.ts`, а не в схеме;
- импорт идёт из сгенерированного пути (`@/generated/prisma/client`), потому
  что поле `output` у генератора стало обязательным;
- пул соединений настраивается средствами драйвера `pg`, а не Prisma.

### Почему `updateTag`, а не `revalidateTag`

Публичные страницы собираются статически, поэтому после правки в админке
кэш нужно сбросить. В Next.js 16 это две разные функции:

- `revalidateTag(tag, profile)` помечает данные устаревшими и обновляет их
  **в фоне** — сразу после сохранения посетитель может увидеть старую версию;
- `updateTag(tag)` истекает **немедленно** и доступен только внутри Server Action.

Для админки нужен второй вариант: автор сохранил и должен сразу видеть
результат. Тег сбрасывается точечно — обновляется всё, что построено
на этих данных, без перечисления адресов страниц.

### Про кэш как границу сериализации

`unstable_cache` сохраняет результат в сериализованном виде. Это не
абстракция, а реальное ограничение, которое проявилось дважды:

- `Map`, возвращённый из запроса настроек, при чтении из кэша превращался
  в пустой объект — пришлось вернуть обычный объект;
- `Date` может вернуться строкой, поэтому `formatDate` принимает и то и другое.

TypeScript об этой границе не знает: компилятор считает, что там `Date`,
а в рантайме приходит строка. Отсюда правило — не доверять типам на границе
кэша.

### Почему парсинг Markdown без `dangerouslySetInnerHTML`

`react-markdown` собирает дерево React-элементов, а не вставляет HTML-строку.
Содержимое из базы не может попасть в страницу как разметка, поэтому XSS
через текст статьи невозможен.

Единственное место, где `dangerouslySetInnerHTML` оправдан, — JSON-LD.
Там символ `<` заменяется на escape-последовательность, иначе закрывающий
тег внутри данных позволил бы внедрить произвольную разметку.

### Почему проверка файла дублируется

Размер файла проверяет и браузер, и сервер. Браузерная проверка экономит
трафик, серверная — единственная, которой можно доверять: клиентские
ограничения обходятся тривиально.

Имя файла обязательно чистится перед записью в хранилище: `../` в имени
позволил бы записать файл куда угодно.

## Тесты

```bash
npm test            # 35 модульных тестов
npm run test:admin  # 30 интеграционных проверок (нужен запущенный сервер)
```

Модульные тесты покрывают чистые функции: транслитерацию slug, устойчивость
дат к строкам из кэша, схемы валидации.

Интеграционные проверки прогоняют реальные сценарии по HTTP, без браузера:
защиту маршрутов, отказ при неверном пароле, вход, создание и правку записи,
инвалидацию кэша, поиск, ограничения загрузки файлов. Формы отправляются
так же, как их отправил бы браузер без JavaScript, — обычным POST
с `multipart/form-data`.

Для запуска интеграционных проверок нужен поднятый сервер:

```bash
npm run build
npm start
# в другом терминале:
npm run test:admin
```

## Деплой на Vercel

1. Загрузите репозиторий на GitHub.
2. В Vercel нажмите **Add New → Project** и подключите репозиторий.
3. В разделе **Storage** создайте **Blob store** — из него возьмётся
   `BLOB_READ_WRITE_TOKEN`.
4. В **Settings → Environment Variables** добавьте:
   - `DATABASE_URL` — строка подключения к Neon (pooled-вариант);
   - `AUTH_SECRET` — тот же секрет, что локально, или новый;
   - `NEXT_PUBLIC_SITE_URL` — адрес будущего сайта, например `https://example.vercel.app`;
   - `BLOB_READ_WRITE_TOKEN` — из созданного Blob store.
5. Нажмите **Deploy**.
6. После первого деплоя примените миграции к продакшен-базе:

```bash
DATABASE_URL="..." npm run db:deploy
```

Отдельный шаг нужен потому, что сборка схему не меняет — она только читает
данные, чтобы отрендерить страницы заранее.

7. Заведите администратора. Сид создаёт демо-запись с известным паролем,
   поэтому для продакшена используйте `prisma/seed.ts` как образец
   и задайте свой пароль.

### Почему сборка требует переменных окружения

Публичные страницы статические, поэтому `next build` обращается к базе,
чтобы отрендерить их заранее. Если `DATABASE_URL` недоступна во время
сборки, сборка упадёт — это ожидаемое поведение, а не ошибка настройки.

## Известные ограничения

Честный список того, что не сделано или сделано упрощённо:

- **Тип файла проверяется по заголовку от браузера.** Он подделывается;
  надёжнее смотреть сигнатуру файла.
- **Поиск через `ILIKE`.** Для портфолио этого достаточно, но на большом
  объёме текста нужен полнотекстовый поиск средствами PostgreSQL.
- **Нет смены пароля из интерфейса.** Пароль задаётся при создании
  администратора.
- **Нет отдельного управления тегами.** Теги рождаются из текста статьи;
  переименовать или удалить их из админки нельзя.
- **Счётчик просмотров не увеличивается.** Поле `views` в схеме есть,
  но инкремент не реализован: мутировать данные во время рендера нельзя,
  а отдельный обработчик не добавлен.
